# Спайк Ф-4.5 — розв'язка viewport від розміру комірки

Перевіряє дев'ять стратегій масштабування одночасно, в одній сітці 3×3, на одній машині.
Проєктне обґрунтування: [`docs/F-4.5-viewport.md`](../../docs/F-4.5-viewport.md).

## Запуск

```powershell
cd spikes\viewport-scaling
npm install
npm start
```

> Windows PowerShell 5.1 не розуміє `&&` — виконуйте команди окремо або розділяйте `;`.

Потрібен Electron ≥ 30 (`WebContentsView`). `npm install` тягне останню версію.

## Що відбувається

1. Створюється вікно 1600×1000 з дев'ятьма `WebContentsView`, кожен зі своєю стратегією.
2. Через 2.5 с знімаються метрики → таблиця **СІТКА 3×3** у терміналі + скріншоти `out/grid-*.png`.
3. Вікно зменшується до 1200×760, сітка перераховується → таблиця **ПІСЛЯ РЕСАЙЗУ** + `out/resized-*.png`.
4. Друкується таблиця **ГІПОТЕЗИ (PASS/FAIL)**.
5. Вікно повертається до 1600×1000 і залишається відкритим для візуальної перевірки.

## Стратегії

| # | Конфігурація | Що перевіряє |
|---|---|---|
| 1 | `baseline` | контроль — як виглядають сигнали С-1…С-4 без втручання |
| 2 | `zoom` | Г-1: `setZoomFactor` дає задану логічну ширину |
| 3 | `zoom+dsf` | Г-2: чи перекриває емульований `deviceScaleFactor` DPR поверх зуму |
| 4 | `zoom+dsf+patch` | Г-5: JS-патч `outer*` / `Screen.prototype` у main world |
| 5 | `dm (no scale)` | контроль для Г-3: чи обрізається вміст без `scale` |
| 6 | `dm+scale` | **Г-3 — ключова гіпотеза** |
| 7 | `dm+scale+dontset` | вплив `dontSetVisibleSize` |
| 8 | `dm+scale+screen` | Г-4: `screenWidth/Height` через CDP |
| 9 | `dm+scale+patch` | цільова комбінація для варіанта D |

## Що дивитись

**У терміналі** — колонки таблиці вердикту (Г-1…Г-6).

**На екрані** — у кожній комірці по краях є смугасті маркери. Якщо **правий маркер не видно**, вміст обрізаний по краю віджета, а не масштабований → стратегія непридатна. Це найнадійніша перевірка Г-3, автоматично вона не визначається.

Також дивіться рядок «верстка»: `МОБІЛЬНА (<768)` червоним означає, що сторінка отримає мобільний лейаут — той самий конфлікт із Ф-4.3, заради якого весь спайк.

**Вручну (Г-8)** — спробуйте відкрити DevTools для будь-якого фрейму. Debugger приєднаний постійно; треба з'ясувати, чи це блокує DevTools і що показує помилка.

**Вручну (Г-9)** — потягніть за край вікна. Ресайз має бути плавним; порівняйте `baseline` з масштабованими комірками. Паралельно подивіться RAM процесу в диспетчері задач.

## Як читати результат

- **№6 або №9 PASS по Г-1/3 + Г-3 clip = ok** → беремо варіант **D** (єдиний механізм через CDP).
- **№6 FAIL, а №2/№3 PASS** → беремо варіант **C + A** (зум + CDP для DPR + JS-патч для `screen`/`outer`).
- **І №2, і №6 FAIL** → лишається **E** (offscreen rendering), етап 4 подовжується на 2–3 тижні.

Результат занесіть у таблицю нижче і оновіть розділ 5 в `docs/F-4.5-viewport.md`.

## Результати

Автоматична колонка «Г3 clip» у таблиці вердикту виявилась ненадійною (це й попереджав розділ «Що дивитись» вище) — вона рахує лише `scrollWidth` сторінки відносно її ж `innerWidth`, а не факт обрізання рендеру по межі віджета. Вона хибно позначала baseline як «ОБРІЗАНО» (сторінка сама по собі ширша за 504 CSS px) і хибно позначала №8/№9 як «ok». Справжня перевірка — розмір PNG від `capturePage()` порівняно з реальними фізичними межами комірки (630×320 при DPR 1.25 для комірки 504×256), плюс візуальний огляд скріншотів.

**Розмір `capturePage()` за конфігурацією (grid, комірка 504×256 → очікувано 630×320):**

| # | Конфігурація | capturePage() | Висновок |
|---|---|---|---|
| 1 | baseline | 630×320 | контроль |
| 2 | zoom | 630×320 | у межах віджета |
| 3 | zoom+dsf | 630×320 | у межах віджета |
| 4 | zoom+dsf+patch | 630×320 | у межах віджета |
| 5 | dm (no scale) | 1600×813 | буфер розрісся до logicalW×DPR |
| 6 | dm+scale | 1600×813 | **`scale` не зменшив буфер — ідентично №5** |
| 7 | dm+scale+dontset | 630×320 | буфер у межах, **але візуально вміст обрізаний, не масштабований** (див. нижче) |
| 8 | dm+scale+screen | 1800×914 | буфер розрісся |
| 9 | dm+scale+patch | 1890×960 | буфер розрісся |

Візуальний огляд `out/grid-*.png` підтверджує: у baseline та в zoom-конфігураціях (№2, №3) смугастий маркер праворуч **видно**, зелена шкала-лінійка вписана в кадр — вміст справді візуально масштабований. У №6, №8, №9 маркер зʼявляється по центру збільшеного полотна — вміст рендериться в повний логічний розмір і обрізається межею `WebContentsView`, просто це не видно на скріншоті, бо `capturePage()` знімає весь (роздутий) буфер, а не те, що фактично лягло б на екран. №7 виглядає найпідступніше: буфер має правильний фізичний розмір, але сам контент усередині намальований у повний нескейлений розмір і тому обрізаний так само, як №6 — просто без розрослого буфера, що маскує проблему для будь-якої перевірки «по розміру файла».

**Висновок: Г-3 FAIL для всіх дев'яти конфігурацій.** `Emulation.setDeviceMetricsOverride` зі `scale` не масштабує вміст візуально в headful `WebContentsView` у жодній комбінації параметрів (з/без `dontSetVisibleSize`, з/без `deviceScaleFactor`, з/без `screenWidth/Height`) — Chromium або розтягує буфер рендеру до логічного розміру (обрізання по межі view), або тримає буфер фізичного розміру, але все одно малює в ньому нескейлений вміст (обрізання всередині того самого буфера). Параметр `scale` для CDP-домену `Emulation` фактично не працює в цьому середовищі (Electron 33.4.11 / Chrome 130, Windows 11, headful `WebContentsView`) — задокументована в CDP поведінка для DevTools/headless тут не відтворюється.

Г-1 і (частково) Г-2 натомість підтверджуються для zoom-конфігурацій:

| Гіпотеза | Результат | Примітка |
|---|---|---|
| Г-1 `setZoomFactor` → logicalW | **PASS** | innerWidth = 1280±1 px для №2/№3, стабільно і до, і після ресайзу |
| Г-2 DPR перекрито профілем | **FAIL** | CDP `deviceScaleFactor` override поверх активного zoom не перекриває `devicePixelRatio` — репортується значення, що дорівнює zoom-scale (0.394…), а не заданому `dsf`. DPR доведеться патчити через JS-гетер (частина варіанта A), а не через CDP |
| Г-3 `scale` масштабує, не обрізає | **FAIL** (усі 9 конфігурацій) | див. розбір вище |
| Г-4 `screenWidth/Height` працює | PASS (для dm-конфігурацій з `screen`) | нерелевантно для обраного варіанта — `screen.*` і так патчиться через JS у варіанті A |
| Г-5 патч main world працює | PASS | `outerHeight − innerHeight ≥ 60` для конфігурацій з `patch: true` |
| Г-6 viewport стабільний при ресайзі | PASS (dm), PASS ±1px (zoom) | 1px розбіжність для zoom — округлення zoom-factor, не логічна помилка |
| Г-7 зум переживає навігацію | не виміряно напряму | `did-finish-load` перевстановлює стратегію при кожному завантаженні — механізм присутній у коді, але цей прогін спайку не робив повторної навігації для перевірки |
| Г-8 DevTools + debugger | **не перевірено** | потребує ручної дії (View → Toggle DevTools) |
| Г-9 продуктивність / RAM | **не перевірено** | потребує ручного спостереження за Диспетчером задач при ресайзі |

**Обраний варіант: C + A** — `setZoomFactor` для масштабу і логічного viewport (Г-1), JS-патч main-world для `outer*`/`screen.*`/`devicePixelRatio` (розширення наявного патч-шару, а не CDP — CDP-шлях для DPR відхилено за результатами Г-2). CDP `Emulation.setDeviceMetricsOverride` не використовується для контролю viewport взагалі; варіант D закрито.

**Побічна знахідка (важливо для реалізації):** будь-яка CDP-команда (`Page.enable`, `Emulation.*`), надіслана через `webContents.debugger.sendCommand` **до першої навігації** `WebContentsView`, підвішує рендерер назавжди без помилки й без відхилення проміса (спостерігалось як «зависання» без CPU-навантаження; за примусового обмеження часу — крах процесу з `crashpad_client_win.cc: not connected`). Мінімальний репро: `debugger.attach()` → одразу `sendCommand()`, без попередньої `loadURL`. Виправлення — прогрівати сесію порожньою навігацією (`about:blank`) одразу після `attach()`, до будь-якої CDP-команди. Це стосується будь-якого майбутнього коду, що використовує CDP на щойно створеному `WebContentsView` (наприклад, `identity/emulation.ts`), і варте окремого регресійного тесту.
