# Аналіз ТЗ: MultiFrame Browser (anti-detect)

**Дата:** 2026-08-01
**Вхідний документ:** `тз.txt`
**Уточнена мета:** anti-detect браузер — сайти не повинні пов'язувати фрейми між собою.

---

## 1. Загальна оцінка

ТЗ описує **ізоляцію сховищ** (cookies, Local Storage, кеш) + **проксі** + **User-Agent**. Це приблизно 30% того, що потрібно для anti-detect. Решта 70% — fingerprint-поверхня, яку поточне ТЗ не згадує взагалі.

Ключовий висновок: **ізоляція cookies ≠ ізоляція ідентичності.** Якщо 9 фреймів мають різні cookies і різні IP, але однаковий canvas hash, однаковий WebGL renderer, однаковий набір шрифтів, однакову таймзону і аномально малий viewport — сучасний анти-фрод (FingerprintJS Pro, Castle, Sift, Cloudflare BM) кластеризує їх за лічені хвилини.

Друга проблема: **сітка 3×3 сама по собі є fingerprint-сигналом.** Фрейм 640×360 на екрані 1920×1080, без chrome-панелей браузера, з нестандартним devicePixelRatio — комбінація, яка практично не зустрічається у реальних користувачів.

Стек Electron + TS + React обрано правильно для MVP, але з важливими застереженнями (розділ 4).

---

## 2. Критичні прогалини

### 2.1. SOCKS5 з логіном/паролем не працює в Chromium

ТЗ вимагає «SOCKS5 — хост, порт, за потреби логін і пароль». **Chromium не підтримує автентифікацію SOCKS5** (username/password, RFC 1929) — це багаторічне обмеження, не баг Electron.

**Рішення:** локальний relay. На старті фрейму піднімати `127.0.0.1:<random>` SOCKS-сервер без авторизації, який форвардить трафік в апстрім з credentials (npm-пакет `socks` / `socksv5`). Фрейму віддається адреса локального relay.

Це окремий компонент із власним життєвим циклом (старт/стоп разом із фреймом, обробка падінь) — має бути в ТЗ як явна вимога.

### 2.2. WebRTC зливає реальний IP

Не згадано в ТЗ. WebRTC ходить по UDP повз HTTP-проксі — реальна IP-адреса витікає навіть при коректно налаштованому проксі. Обов'язково:

```
webContents.setWebRTCIPHandlingPolicy('disable_non_proxied_udp')
```

Плюс тест у критеріях приймання: `browserleaks.com/webrtc` не показує реальний IP у жодному фреймі.

### 2.3. Kill-switch при падінні проксі

ТЗ описує, що робити при помилці проксі («показується у відповідному фреймі»), але не забороняє fallback на пряме з'єднання. Якщо в `proxyRules` вказати кілька значень або залишити `DIRECT` у ланцюжку — Chromium піде напряму і зіллє IP.

**Вимога:** для фрейму з проксі пряме з'єднання має бути неможливим на рівні конфігурації. При недоступності проксі — фрейм показує помилку і не завантажує нічого.

### 2.4. User-Agent без Client Hints — миттєвий детект

`webContents.setUserAgent()` змінює тільки рядок UA. `navigator.userAgentData` і заголовки `Sec-CH-UA*` залишаються від Electron/Chromium за замовчуванням. Розбіжність між UA-рядком і Client Hints — один із найпростіших детекторів спуфінгу.

**Рішення:** через CDP (`webContents.debugger`):

```
Emulation.setUserAgentOverride({
  userAgent, acceptLanguage, platform,
  userAgentMetadata: { brands, fullVersionList, platform, platformVersion, architecture, model, mobile }
})
```

### 2.5. Версія Chromium в Electron відстає від stable Chrome

Якщо UA заявляє Chrome 141, а движок — Chromium 134, feature-detection покаже невідповідність (відсутні нові API, інша поведінка CSS). 

**Вимога:** UA-шаблони генеруються від **фактичної** версії Chromium у збірці Electron, а не довільно. Оновлення Electron — частина релізного циклу, не «колись потім».

### 2.6. Розміри вікна та екрана

Найнедооціненіший ризик. У сітці 3×3 кожен фрейм отримує ~640×360 CSS-пікселів, при цьому `screen.width/height` повідомляють реальні 1920×1080, а `window.outerHeight === innerHeight` (немає chrome браузера).

**Рішення:** `Emulation.setDeviceMetricsOverride` — задавати логічний viewport (напр. 1280×720), `deviceScaleFactor`, а також `screenWidth/screenHeight`. Рендер відбувається у логічному розмірі, візуально масштабується у комірку сітки. Це змінює архітектуру відображення і має бути закладено з першого дня.

### 2.7. Відсутній `window.chrome` та інші «сліди Electron»

Electron не має `window.chrome.runtime`, `chrome.loadTimes`, PDF-viewer plugin, має свій набір `navigator.plugins`. Плюс класика: розбіжність `Notification.permission` і `navigator.permissions.query({name:'notifications'})`.

Патчі потрібно інжектити **у main world до виконання скриптів сторінки** — через `Page.addScriptToEvaluateOnNewDocument` (CDP). Preload з `contextIsolation: true` тут не підійде: він працює в isolated world і не бачить main world.

### 2.8. Fingerprint-поверхня, яку треба закрити

| Вектор | Підхід |
|---|---|
| Canvas 2D | Детермінований шум на `toDataURL`/`getImageData`, seed від ID фрейму |
| WebGL | Спуф `getParameter` (VENDOR, RENDERER, UNMASKED_*), шум на `readPixels` |
| AudioContext | Шум на `getChannelData`/`getFloatFrequencyData` |
| Timezone | `Emulation.setTimezoneOverride` — **обов'язково узгоджено з країною проксі** |
| Geolocation | `Emulation.setGeolocationOverride` + permission policy |
| Locale / Accept-Language | `Emulation.setLocaleOverride` + `acceptLanguages` |
| Шрифти | Найскладніше. Патч `measureText`/`offsetWidth` або обмеження списку через CDP |
| `navigator.hardwareConcurrency`, `deviceMemory` | JS-патч, значення з профілю |
| ClientRects | Субпіксельний шум |
| Battery, Media devices, Gamepad | Стабільні значення з профілю |

### 2.9. Чесне обмеження, яке треба зафіксувати в ТЗ

Усі 9 фреймів працюють на **одній машині, одному GPU, одній ОС, одному бінарнику Chromium**. Апаратна ентропія (модель GPU через ANGLE, TCP/TLS-фінгерпринт стека ОС, набір системних шрифтів) спільна. 

Тому мета має бути сформульована як: **кожен фрейм виглядає як правдоподібний типовий пристрій**, а не як унікальний. Спроба зробити кожен фрейм «унікальним» дає протилежний ефект — унікальність сама стає ідентифікатором.

### 2.10. TLS/HTTP2 fingerprint (JA3/JA4) — поза межами Electron

Chromium має характерний JA3. Всі фрейми матимуть однаковий. Обійти без патчу Chromium або без резидентних проксі з TLS-термінацією неможливо. **Зафіксувати як відомий ліміт MVP.**

## 3. Функціональні прогалини (не пов'язані з детектом)

Не описано в ТЗ, але потрібно для працездатного продукту:

- **Профілі/пресети** — фрейм має бути іменованим профілем (ім'я, проксі, fingerprint-набір, стартовий URL), який можна зберегти, скопіювати, експортувати/імпортувати. Зараз ТЗ прив'язує все до позиції в сітці, що незручно.
- **Імпорт списку проксі** — `host:port:user:pass` рядками з файлу/буфера, масове призначення на фрейми.
- **Перевірка проксі** — визначено як «перевіряє доступність», але не сказано як. Треба: запит до IP-echo сервісу, таймаут (напр. 10 с), відображення exit-IP, країни, latency.
- **Нові вікна / popup** — `window.open`, `target=_blank`. Потрібен `setWindowOpenHandler`: відкривати в тому ж фреймі, або вкладки всередині фрейму (важливо для OAuth-логінів).
- **Завантаження файлів** — окрема тека на фрейм, черга завантажень.
- **Помилки сертифікатів** — багато проксі роблять MITM. Політика: блокувати / питати / довіряти конкретному.
- **Максимізація одного фрейму** — при 3×3 працювати в комірці неможливо. Потрібен режим «розгорнути фрейм на все вікно» по подвійному кліку/хоткею.
- **Модель фокусу** — який фрейм отримує клавіатуру, візуальна індикація активного фрейму.
- **DevTools на фрейм** — для налагодження (з попередженням, що відкриті DevTools можуть змінювати поведінку).
- **Очищення даних фрейму** — кнопка «скинути профіль» без перезапуску програми.
- **Логи та діагностика** — журнал проксі-помилок, експорт для підтримки.
- **Авто-оновлення + підпис коду** — без code signing Windows SmartScreen блокуватиме інсталятор.
- **Локалізація** — UA/EN.

## 4. Архітектурні рішення

### 4.1. Electron — так, але `WebContentsView`, не `<webview>`

Тег `<webview>` офіційно не рекомендований, нестабільний, повільний. `BrowserView` застарілий. Використовувати **`WebContentsView`** (Electron 30+).

**Наслідок:** `WebContentsView` не є частиною DOM. React рендерить «примарну» сітку (плейсхолдери), main-процес позиціонує реальні view поверх, координати синхронізуються через IPC на кожному resize. Це нетривіально — закласти час, вирішити проблему лагу при ресайзі (debounce + приховування view під час drag).

### 4.2. Ізоляція = окрема `session` на фрейм

```
session.fromPartition('persist:frame-<uuid>')  // чекбокс УВІМКНЕНО
session.fromPartition('frame-<uuid>')          // ВИМКНЕНО → in-memory, зникає при закритті
```

Це елегантно лягає на вимогу ТЗ щодо чекбокса. **Але:** partition не змінюється в рантаймі. Перемикання чекбокса вимагає перестворення `WebContentsView` — визначити поведінку (запит підтвердження + перезавантаження фрейму).

Проксі задається **на сесію**, не на webContents — тобто окрема сесія на фрейм є обов'язковою умовою і для проксі теж.

### 4.3. Проксі-автентифікація

- HTTP/HTTPS-проксі: подія `app.on('login', ...)` з `authInfo.isProxy === true`; мапити `webContents` → фрейм → credentials.
- SOCKS5: локальний relay (див. 2.1).

### 4.4. Безпека shell-застосунку

Обов'язково, і має бути в ТЗ явно: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, заборона навігації головного вікна, CSP, валідація URL перед завантаженням, жодних Node-API в preload фреймів.

### 4.5. Паролі

Electron `safeStorage` (DPAPI під капотом). Застереження: шифротекст прив'язаний до Windows-акаунта і машини — при перенесенні профілю на інший ПК паролі не розшифруються. Передбачити коректну обробку помилки та експорт конфігу без паролів.

### 4.6. Ресурси

9 незалежних сесій Chromium — реалістично 2.5–4 ГБ RAM. Потрібно:
- ліниве створення фреймів (view створюється при першому переході, не на старті);
- «присипляння» неактивних фреймів (`backgroundThrottling`, за потреби — вивантаження view зі збереженням URL);
- бюджет у нефункціональних вимогах: наприклад, ≤ 350 МБ на фрейм у стані idle.

**Не** зменшувати `--renderer-process-limit` — це зламає ізоляцію процесів між фреймами.

### 4.7. Запасний шлях

Якщо детект стане блокером — наступний рівень це власна збірка Chromium із патчами на рівні C++ (canvas, WebGL, JA3). Це в рази дорожче. Архітектуру варто будувати так, щоб шар «browser engine» був відокремлений від UI і замінюваний.

## 5. Критерії приймання — переписати на вимірювані

Поточні критерії якісні («працює незалежно»), їх не можна ані пройти, ані провалити однозначно. Пропозиція:

**Ізоляція**
1. Логін у три різні акаунти одного сервісу в трьох фреймах одночасно; жоден не розлогінює інші після 30 хв роботи та після перезапуску.
2. `document.cookie`, IndexedDB, Local Storage, Cache Storage, Service Workers одного фрейму недоступні з іншого (автотест).

**Мережа**
3. Exit-IP кожного фрейму відповідає призначеному проксі (перевірка через IP-echo).
4. WebRTC-тест не показує реальний IP у жодному фреймі.
5. DNS-тест не показує локального резолвера.
6. При зупинці проксі фрейм показує помилку і **не** завантажує сторінку напряму.

**Fingerprint**
7. `creepjs` / `fingerprint.com` дають різні visitorId для всіх 9 фреймів у 10 послідовних запусках.
8. UA-рядок і `navigator.userAgentData` узгоджені; версія відповідає фактичному Chromium.
9. Таймзона і `Accept-Language` фрейму відповідають країні його проксі.
10. `window.screen`, `innerWidth/Height`, `devicePixelRatio` — правдоподібна комбінація незалежно від розміру комірки сітки.
11. Детектори автоматизації (`navigator.webdriver`, permissions-mismatch, відсутність `window.chrome`) — чисто.

**Продуктивність**
12. Холодний старт до робочої області ≤ 5 с.
13. 9 фреймів з відкритими сторінками ≤ 4 ГБ RAM.
14. Відновлення сесії ≤ 10 с.

**Персистентність**
15. Профіль із увімкненим збереженням відновлює URL, cookies, LS, проксі, UA і fingerprint-набір.
16. Профіль із вимкненим — після перезапуску має порожній стан; на диску немає залишків (перевірка теки Partitions).
17. Паролі проксі відсутні у відкритому вигляді в будь-якому файлі на диску (grep по userData).

## 6. Етапи розробки

Оцінки — для одного досвідченого розробника. Паралелізація можлива з етапу 3.

### Етап 0. Технічні спайки (1–1.5 тижні)
Перевірити ризики до написання архітектури. **Без цього етапу планування не має сенсу.**
- Per-session проксі + автентифікація HTTP-проксі.
- SOCKS5 relay з авторизацією — робочий PoC.
- `WebContentsView` у сітці 3×3 з ресайзом — оцінити плавність.
- CDP `Emulation.setUserAgentOverride` + `setDeviceMetricsOverride` + `setTimezoneOverride` на webContents.
- `Page.addScriptToEvaluateOnNewDocument` — інжекція патчу в main world.
- Заміри RAM для 9 сесій.

**Вихід:** підтверджені/спростовані припущення, рішення щодо стека зафіксоване.

### Етап 1. Каркас (1.5 тижні)
Electron + TS + React, розділення main/renderer, типізований IPC-контракт, схема конфігу з версіонуванням і міграціями, екран запуску (вибір 1–9 фреймів, чекбокс відновлення), сітка з порожніми комірками, логування, збірка та інсталятор (NSIS) у CI.

### Етап 2. Ядро фрейму (2 тижні)
`WebContentsView` на партиції, адресний рядок, назад/вперед/оновити, індикатор завантаження, сторінки помилок, `setWindowOpenHandler`, вкладки всередині фрейму (мінімум для OAuth), фокус, максимізація фрейму, hardening (sandbox, contextIsolation).

**Вихід:** 9 незалежних браузерів без проксі та спуфінгу. Проходять критерії 1–2.

### Етап 3. Мережевий шар (2–2.5 тижні)
Режими Direct / HTTPS / SOCKS5, валідація полів, `app.on('login')`, SOCKS5-relay як керований підпроцес, перевірка проксі з показом exit-IP і країни, kill-switch, WebRTC-політика, індикатор режиму, імпорт списку проксі.

**Вихід:** критерії 3–6.

### Етап 4. Ідентичність та fingerprint (3–4 тижні) — найризикованіший
- Модель «профіль пристрою»: UA + UA-CH + platform + screen + hardwareConcurrency + deviceMemory + GPU + шрифти, генерована з правдоподібних наборів.
- Інжекція патчів у main world: canvas, WebGL, audio, ClientRects, `window.chrome`, permissions.
- `setDeviceMetricsOverride` — розв'язка логічного viewport від розміру комірки.
- Timezone/locale/geo, автоматично прив'язані до країни проксі.
- Вбудовані шаблони UA + власний UA.
- Внутрішня сторінка самоперевірки (прогін по creepjs/browserleaks з наочним звітом).

**Вихід:** критерії 7–11.

### Етап 5. Персистентність (1.5 тижні)
Збереження/відновлення сесій за чекбоксом, `safeStorage` для паролів, гарантоване очищення даних вимкнених профілів, менеджер профілів (створити/копіювати/скинути/експорт-імпорт без паролів), відновлення при зміні кількості фреймів.

**Вихід:** критерії 15–17.

### Етап 6. UX та продуктивність (2 тижні)
Ліниве створення та присипляння фреймів, завантаження файлів, обробка помилок сертифікатів, гарячі клавіші, DevTools на фрейм, локалізація UA/EN, налаштування застосунку, оптимізація ресайзу сітки.

**Вихід:** критерії 12–14.

### Етап 7. Стабілізація та реліз (2 тижні)
Автотести (Playwright for Electron) на матрицю приймання, довготривалий прогін (8+ год), обробка падінь renderer, crash-репорти, авто-оновлення, підпис коду, документація, приймальне тестування.

**Разом: 15–19 тижнів** до релізу v1.0. MVP «без fingerprint-шару» (етапи 0–3, 5) — приблизно 8–9 тижнів.

## 7. Ризики

| Ризик | Вплив | Пом'якшення |
|---|---|---|
| Детект попри спуфінг (JA3, апаратна ентропія) | Високий | Етап 0 + сторінка самоперевірки; закласти можливість переходу на патчений Chromium |
| Лаг/мерехтіння `WebContentsView` при ресайзі | Середній | Перевірити на етапі 0; debounce + приховування під час drag |
| SOCKS5-relay як точка відмови | Середній | Health-check, авто-рестарт, деградація в явну помилку фрейму |
| RAM понад бюджет на слабких ПК | Середній | Ліниве створення + присипляння; попередження при виборі 9 фреймів |
| Оновлення Electron ламає CDP-патчі | Середній | Регресійні тести fingerprint у CI на кожен апгрейд |
| Порушення ToS сайтів кінцевими користувачами | Юридичний | Дисклеймер в EULA; продукт позиціонується як інструмент, відповідальність на користувачі |

## 8. Що змінити в ТЗ найперше

1. Додати розділ **«Профіль ідентичності»** — весь пункт 2.8 як окремі функціональні вимоги.
2. Переписати SOCKS5 із явною вимогою локального relay.
3. Додати WebRTC / DNS / kill-switch до розділу «Мережеві налаштування».
4. Замінити «фрейм» на «профіль» як основну сутність; позиція в сітці — лише відображення.
5. Замінити критерії приймання на вимірювані (розділ 5).
6. Додати нефункціональні вимоги: RAM, час старту, безпека Electron.
7. Додати розділ «Відомі обмеження» з пунктами 2.9 і 2.10 — щоб очікування були реалістичні з самого початку.
